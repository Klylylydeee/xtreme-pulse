# Changelog

Notable changes to Xtreme Pulse, newest first. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/). Record each build phase as it ships, and any spec change that alters behavior.

## [Unreleased]

### Spec changes

- 2026-10-05: Step 1.6 spec (before the build). Module access is stored as `users.moduleAccess`, one level per module (Insight None or Read only), with a missing value read as None, so no migration; it is only read until step 1.7 adds the setter ([Resolving and enforcing](SECURITY.md#resolving-and-enforcing-build-step-16), [DATA_MODEL.md](docs/DATA_MODEL.md#collection-ownership)). The System Administrator, the bootstrap system account included, resolves to Owner on every module and Read on Insight whatever is stored ([System Administrator](SECURITY.md#system-administrator)). Pages, Server Actions and Route Handlers check access themselves through one shared check (`requireModuleAccess`, `requireModulePage`); the proxy stays the sign-in and status check. A blocked page answers HTTP 403 with a designed no-access state inside the shell, replacing the not-found page with HTTP 200 on the admin pages; guarded pages put their guard first and use in-page `<Suspense>`, with no route-level `loading.tsx` above them ([Pages, Server Actions and Route Handlers](docs/CODE_STYLE.md#pages-server-actions-and-route-handlers)). The `/admin` pages are checked by role (`requireAdminPage`), and the sidebar shows an Administration group to HR (Overview, Users, Departments, Positions) and the System Administrator (also Company settings and Audit log) ([Administration area](docs/modules/core.md#administration-area), [One application](docs/ARCHITECTURE.md#one-application)). Home shows "Your access is being set up" to anyone with None on every module, and unknown URLs get a designed 404 page ([Feedback & motion](docs/DESIGN_SYSTEM.md#feedback--motion)). The file route checks each owner type through a registration, answers a refused file like a missing one (404), and no longer refuses every file in production ([File storage](docs/ARCHITECTURE.md#file-storage), [Exceptions to module access](SECURITY.md#exceptions-to-module-access)). `noAccessCheckYet` is removed. The review checklist accepts a Pulse Core check (signed in, or the admin area role) ([Review checklist](SECURITY.md#review-checklist)). `pnpm test` adds the module access tests ([TESTING.md](docs/TESTING.md#module-access-tests), [ADR 0010](docs/adr/0010-manual-verification-before-automated-tests.md)). Decisions 50 to 64 in [BUILD_PLAN.md](docs/BUILD_PLAN.md#decisions-added-to-the-spec).
- 2026-10-05: Step 1.5 review fixes. A user signed out while several requests are in flight (for example two Server Actions from one click) now always lands on the login page with "You were signed out": refusing a session also sets a one-minute `pulse-signed-out` flag cookie (value `1`, nothing about the user) that the later redirects read, and a valid session clears it. A create or email change on a domain that is removed at the same time is refused: the save writes the domain record inside its transaction ([Managing user accounts](docs/modules/core.md#managing-user-accounts)). The last-System-Administrator guard re-checks, inside the transaction, that the acting System Administrator is still active ([Account status](SECURITY.md#account-status)). When HR saves a System Administrator's row, the posted email is ignored and the stored one kept, so a stale form no longer fails. The separation date is worded as required for a separated status (Resigned, Terminated, Retired), null otherwise, as built. Reporting lines: an edit that only removes or reorders supervisors isn't re-checked ([Reporting lines](docs/modules/core.md#reporting-lines)). [Roles](SECURITY.md#roles): HR moving someone into or out of HR changes that person's role, and it is audited. Known limit recorded: a future-dated hire can't be separated before their date hired and employees can't be deleted, until date-aware statuses (possibly Phase 2). The users list fits 1280px with the sidebar open (badges under the name, the email shortened), starts sorted by Name (last name) so the phone control reads "Sort by Name", and the reset confirmation warns when unsaved edits in the form will be lost. New tests in `users.test.ts`; `user-accounts.test.ts` and `employees/model.test.ts` are listed in [TESTING.md](docs/TESTING.md#user-account-tests).
- 2026-10-05: Step 1.5 spec (before the build). `/admin/users` lets HR and the System Administrator create and edit the identity Core owns (email, name, employee number, date hired, department, position, employment status, separation date, `reportingTo`) until module access in step 1.6; new users are never System Administrators, nobody edits their own row, and only another System Administrator changes a System Administrator's email or status or resets their password; the bootstrap system account shows only to System Administrators ([Managing user accounts](docs/modules/core.md#managing-user-accounts), [System Administrator](SECURITY.md#system-administrator)). Temporary passwords are generated by the server (16 Crockford base32 characters), shown once and never stored in plain text, logged or audit-logged; a reset ends all the user's sessions through the new `users.sessionsValidFrom`, while changing one's own password still keeps them; nobody resets their own password there ([Sign-in and passwords](SECURITY.md#sign-in-and-passwords)). The new `employees.separationDate` is required for Resigned and Retired and must be today or earlier for now; status changes take effect at once; Terminated stays unavailable until Phase 2; a separated employee can be moved back to an active status; a change that would leave no active System Administrator is refused ([Account status](SECURITY.md#account-status), [Derived values](docs/DATA_MODEL.md#derived-values)). Employee numbers are generated inside the create transaction, never fill gaps, and an entered company ID must match the date hired's year ([Employee number](docs/modules/core.md#employee-number-company-id)). Anyone may have an empty `reportingTo`, not only Board members; supervisors are limited to 10 active employees, and cycles are refused also under concurrent edits ([Reporting lines](docs/modules/core.md#reporting-lines)). A department head who separates stays set with an "Inactive" badge ([Managing departments and positions](docs/modules/core.md#managing-departments-and-positions)). `pnpm test` adds the user account tests ([TESTING.md](docs/TESTING.md#user-account-tests), [ADR 0010](docs/adr/0010-manual-verification-before-automated-tests.md)). Decisions 31 to 49 in [BUILD_PLAN.md](docs/BUILD_PLAN.md#decisions-added-to-the-spec).
- 2026-10-05: Step 1.4 review fixes. Position names are unique within a department ignoring case (`Driver` and `driver` are the same name), retired positions included; the unique index now uses a case-insensitive collation, and `pnpm seed:admin` drops the old case-sensitive index on an existing database ([Managing departments and positions](docs/modules/core.md#managing-departments-and-positions)). Adding or restoring a position and retiring its department at the same time, or removing two allowed email domains at the same time, can no longer both succeed against the rules (no live position in a retired department, never zero allowed domains). Position audit labels read `<department code> · <position name>`, like department labels (`<department code> · <department name>`) ([Managing departments and positions](docs/modules/core.md#managing-departments-and-positions)). The seed drops the old position name index only once the case-insensitive one exists, and otherwise keeps it and prints a warning. A System Administrator-only action refused for anyone else now says "Only the System Administrator can do this." A `.gitattributes` file keeps text files LF in the repository. An uploaded company logo sits on a new `logo-tile` token, a white tile with a hairline border that stays the same in dark mode, so a transparent logo with dark ink stays legible on the login hero and in the dark sidebar ([Color: Cobalt palette](docs/DESIGN_SYSTEM.md#color-cobalt-palette)).
- 2026-10-03: Step 1.4 departments, positions and company settings (spec, before the build). `/admin/departments` and `/admin/positions` are for HR and the System Administrator, and `/admin/settings` (company details, logo, allowed email domains, upload settings) for the System Administrator only, until module access in step 1.6; services re-check the role, and every change is audit-logged in the same transaction (`core.department`, `core.position`, `core.companySettings`, `core.allowedEmailDomain`, `core.configVersion`). Department codes are fixed and never reused; a position's department is fixed; a timesheet type change takes effect from the next cut-off. A department can't be retired while it has live positions or active employees, nor a position while active employees hold it; `HR`, `ACCT` and `BOD` follow the same rules. Retiring is a soft delete (audit `delete`) and can be undone (audit `restore`). A department head is any active employee ([Managing departments and positions](docs/modules/core.md#managing-departments-and-positions)). System-wide settings are the upload limits, versioned from today in Manila, one change per day. Re-adding a removed email domain restores it; removing the last domain or the acting admin's own domain is refused. The logo counts as a company detail; while any detail is a placeholder, HR and the System Administrator see a banner on Home and `/admin`, and a weekly job (Mondays 8:00 AM Manila, at most once per recipient per day) notifies them ([Company settings page](docs/modules/core.md#company-settings-page), [Background jobs](docs/ARCHITECTURE.md#background-jobs)). The logo is served without sign-in by a narrow `/company-logo` route, an exception to module access ([Exceptions to module access](SECURITY.md#exceptions-to-module-access), [File storage](docs/ARCHITECTURE.md#file-storage)). `pnpm test` adds the Core administration tests ([TESTING.md](docs/TESTING.md#core-administration-tests), [ADR 0010](docs/adr/0010-manual-verification-before-automated-tests.md)). Decisions 20 to 30 in [BUILD_PLAN.md](docs/BUILD_PLAN.md#decisions-added-to-the-spec).
- 2026-10-03: Step 1.3 follow-up. On an update, services snapshot both sides with `snapshotsForAudit`, and a sensitive field whose stored encrypted value changed (or is new) is stored as `{ "$hidden": "sensitive", "changed": true }` in `after` and shown as "Hidden (sensitive), changed" on the audit page; only the stored bytes are compared, and nothing of the value or ciphertext is kept. Re-saving the same value also counts as a change, since encryption is randomized ([Audit logging](SECURITY.md#audit-logging)). The reveal rules now say explicitly that an employee may reveal every category on their own record and that HR may reveal other HR staff's values ([Sensitive data](SECURITY.md#sensitive-data)).
- 2026-10-03: Step 1.3 audit log, notifications and sensitive reveal (server side). New Core collections `auditLogs` and `notifications`, both kept forever with no expiry, by the project owner's decision ([Retention](docs/DATA_MODEL.md#retention), [Record retention](docs/COMPLIANCE.md#record-retention)). Audit entries hold full redacted `before`/`after` snapshots, are append-only, and are written with `recordAudit` in the same transaction as the change they record, so a failed entry fails the change ([Audit log](docs/modules/core.md#audit-log), [Audit logging](SECURITY.md#audit-logging), [Architecture rules](docs/ARCHITECTURE.md#architecture-rules)). Password changes are audit-logged. Notification links must be paths inside the app; only `readAt` can change ([Notifications](docs/modules/core.md#notifications)). Revealing a sensitive value needs a signed-in user, a registered record type and field, and the reveal rules (System Administrator, HR, Accounting, the employee's own record, and the Board for HR-department pay and IDs); the entry is committed before the value is returned ([Sensitive data](SECURITY.md#sensitive-data), [ADR 0005](docs/adr/0005-field-level-encryption.md)). The `MODULES` constant is now in `@pulse/core`. `pnpm test` also runs the audit, notification and reveal tests ([TESTING.md](docs/TESTING.md#audit-notification-and-reveal-tests), [ADR 0010](docs/adr/0010-manual-verification-before-automated-tests.md)).

- 2026-10-03: The dev server accepts other devices on the network. In development only, `allowedDevOrigins` is the computer's own IPv4 addresses plus the optional `DEV_ALLOWED_ORIGINS` list, so a page opened by LAN IP (for example on a phone) hydrates instead of having `/_next/hmr` blocked. Production is unchanged ([Environment variables](docs/DEPLOYMENT.md#environment-variables)).
- 2026-10-03: Step 0.8 completed ([ADR 0012](docs/adr/0012-fail-closed-sensitive-fields.md), [ADR 0005](docs/adr/0005-field-level-encryption.md), [Sensitive data](SECURITY.md#sensitive-data)). The `$jsonSchema` validator is installed with each model's indexes and uses MongoDB's `encrypt` keyword, which pins binary subtype 6 on Community. `null` is refused in a sensitive field (absent is allowed; clear with `$unset`), container types on the way to a sensitive path are pinned, and `strict: false` (schema option or write option) and `bypassDocumentValidation` are refused. `$out` keeps the validator and validates. `pnpm test` runs the guard suite with Vitest against a throwaway `mongodb-memory-server` replica set ([Sensitive-data guard tests](docs/TESTING.md#sensitive-data-guard-tests)).
- 2026-10-03: Known limits of the sensitive-field guard accepted ([ADR 0012](docs/adr/0012-fail-closed-sensitive-fields.md#consequences), [Sensitive data](SECURITY.md#sensitive-data)). Mongoose's `middleware: false` option and `connection.bulkWrite` skip the guard: with `bypassDocumentValidation` they store plain text, and without it a plain value or `null` can become an empty placeholder. Code must never use them; ESLint bans the `middleware` and `bypassDocumentValidation` option keys and `bulkWrite` on a connection, and reviews check the rest. An upsert filter that reaches a sensitive field through `$in`, `$nin`, `$all` or `$elemMatch` is now refused too.
- 2026-09-27: Step 1.2 sign-in and passwords ([Sign-in and passwords](SECURITY.md#sign-in-and-passwords)). The password rule is 12 to 128 characters with no composition rules; a new password must differ from the current one and from the email, and its confirmation must match. Temporary passwords follow the same rule, minus the check against the current password. Changing a password requires the current one and doesn't end other sessions (step 1.5 decides that). The 24-hour session is absolute from sign-in, not extended by activity. Sign-ins are never audit-logged; password changes are from step 1.3. New environment variable `AUTH_TRUST_HOST=true` ([Environment variables](docs/DEPLOYMENT.md#environment-variables)).
- 2026-09-27: Step 1.1 seed rules ([Bootstrap System Administrator account](docs/modules/core.md#bootstrap-system-administrator-account)). A seed loader may fill a field that is absent on an existing record but never changes an existing value. Seeded positions carry a stable seed key, so a renamed seeded position isn't added again. Seed writes are system writes (`createdBy` null), are not audit-logged and are not backfilled when the audit log arrives in step 1.3. The allowed-domain check runs in services against the stored `allowedEmailDomains`, not in the users schema, whose email validator now checks only the email's shape. [Architecture](docs/ARCHITECTURE.md#modules-and-packages): module schemas, Core's included, live in their module package; `packages/db` holds the connection and model helpers and only the shared master data added in step 1.8.
- 2026-09-27: Sensitive fields fail closed ([ADR 0012](docs/adr/0012-fail-closed-sensitive-fields.md)). `sensitiveField()` is limited to single-value fields and fields in arrays of subdocuments; other shapes throw when the schema is defined, and `strict: false` writes, `$rename` of sensitive paths and upserts filtering on them are refused. Every collection with sensitive paths gets a `$jsonSchema` validator, installed with its indexes, that rejects plain values. The guard gets the first automated tests, run by `pnpm test` ([Sensitive data](SECURITY.md#sensitive-data), [Sensitive-data guard tests](docs/TESTING.md#sensitive-data-guard-tests)).
- 2026-09-27: Allowed email domains are stored records (`allowedEmailDomains`) that the System Administrator manages; `ALLOWED_EMAIL_DOMAINS` is only the default list `pnpm seed:admin` loads ([Sign-in and passwords](SECURITY.md#sign-in-and-passwords)).
- 2026-09-27: Local development no longer uses Docker. MongoDB 8 Community Server (as the single-node replica set `rs0`) and Redis (on Windows, Memurai or a Windows port) are installed locally; setup is in [README.md › Getting started](README.md#getting-started). `docker-compose.yml` is removed.

- 2026-09-25: Files are stored in a `storage/` folder with the app instead of S3-compatible storage (MinIO), and open only through an access-checked route ([ADR 0011](docs/adr/0011-file-storage-in-project-folder.md)).
- 2026-09-25: Answered the four security questions. HR, Accounting and Board roles come from the department. Only a System Administrator resets a System Administrator's password. HR staff's pay and bank details are changed only by the System Administrator or a Board member. Sessions last 24 hours.
